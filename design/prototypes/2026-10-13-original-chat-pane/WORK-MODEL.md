# 工作模型核对：2026-10-13

当前原型存在实质遗漏：沿用旧 UI 的「Agent 的 / 人类的」两本账，且把进展写成独立 Progress / Step 模型。两者都没有正确表达后续已拍板的工作模型。README 中相关描述与当前画板仅代表上一轮草图，不再作为工作模型依据；画板尚未按本核对结果重做。

## 已有决定的来源

`docs/superpowers/specs/2026-10-05-crewd-backend-and-work-tracking-design.md` §24.1，尤其第 893–896 行：

- 一本账，三种条目：原始需求、计划、待人类处理，互相连边。
- 稳定编号全组织唯一，永不复用；另有可读代号。挪到新父项下重编可读代号，旧代号仍可跳转；最多三层。
- 进度表是计划项上的视图。群、session、机组里引用同一份视图，修改不产生副本。
- 每项一个覆盖式备注栏。
- 待人类处理是全组织一个收件箱，包含上下文与推荐选项，可回答、稍后、不要了；事项结束自动撤回。
- 允许自建任意类型的表，基于对象类型、链接、动作、视图。
- 完成由负责的 agent 标记，可附文字凭据；不引入额外的人或系统验收门槛。

三种条目不等于固定串联的三层；层级、来源、依赖、卡点和分类必须分别表达。具体深度计算及写入规则仍需和后端当前契约核对，不从 UI 自行定义另一套。

只读检查后端 worktree `crewd/crates/proto/src/work.rs` 与 `crewd/crates/work/src/model.rs`：计划已有稳定 ID、parent、dependsOn、sources、owner、status、blockedOn、nextCheckAt、revision、目标、完成层级、验收标准、证据、当前备注及按需交接历史等字段。读取源码只证明字段存在，不证明本原型已接入或运行态已验收。

## 下一版设计建议（尚未作为用户新决定）

Todo tab 中以「原始需求 / 计划 / 待人类处理」组织同一账本的三个视图；文件夹是独立分类维度。原始需求展开显示关联计划；计划显示最多三层结构和稳定编号；待人类处理引用唯一事项并显示来源，不能在每个机组复制一份。聊天右侧 Todo 只作当前会话相关记录的摘要引用。

进展默认用可折叠的层级表：代号/标题、状态、负责人、下一步、下一检查、卡点、最近更新。展开详情包含目标、完成层级、验收标准、源需求、依赖、待人类事项、产物/证据和交接历史。树表达 parent，依赖在行内以可跳转引用表达；需要时可添加依赖视图，默认不铺 DAG 图。不凭已完成子项数量制造精确百分比。

数据层复用 Plan / WorkItem，来源和依赖用稳定 ID；另设分类关系和 ViewDefinition（范围、文件夹、过滤、排序、列、分组、展开偏好）。进展是查询和呈现，没有自己的工作状态副本。agent 可自由组织分类与视图，不能由改文件夹隐式修改负责人、依赖或完成状态。

自建表使用类型定义、类型字段、带类型的行值、对象引用与视图配置；字段可以是文本、数值、日期、枚举、对象引用等，避免只有自由 JSON blob 或 Markdown，导致人和 agent 无法一致查询。固定工作字段继续遵守后端工作模型，不被自定义列覆盖。

## 防止跨 session 遗漏

设计前从本文件列出的有效裁定与当前后端契约核对，不仅参考旧 UI。设计需求记录应标注用户已定 / 设计建议 / 未确认、来源与被替代关系；新一轮变更检查导航、工作模型、分组、权限、状态及数据引用是否一起保留。若存在无法取回的决定，明确指出缺口并请用户只补该点，不替用户编造。

本文件只更新设计目录。未更改共享 spec、后端、产品 UI 或持久记忆；两个 session 仍需要明确交接，不能假定自动同步。

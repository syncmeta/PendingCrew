## Attachment authority and migration contract

Original M3a data-and-api plan line50, decision14 explicitly records that the upload protocol is not defined, every nonempty message.post attachments request is refused (-32602), and client-provided paths are rejected to prevent path injection; M1 imported old attachments remain listed. This text is under the plan's writing-time decisions, not an independently recovered verbatim human chat authorization. QA preserves the existing implemented contract and does not reinterpret it as permission to implement upload.

Current owning source agrees: proto params.rs AttachmentParam and MessagePostParams document the refusal; server dispatch.rs message.post passes Human input into collab messages.rs, where nonempty attachments are rejected without a sender exception. Remote authorized connections converge on the same conn/dispatch handler. Agent port.rs post additionally rejects its nonempty Vec<String>, and agent tools send only empty attachments; agent read formatting merely includes existing attachment paths in text. This is not a working agent upload protocol.

Original CrewChatAdapter preserves historical attachment metadata; BubbleView currently opens only file:// URLs and has no authenticated remote byte loader. Complete frontend migration must distinguish (1) historical authorized message metadata display, (2) agent textual references to already visible paths and (3) human/remote upload and remote byte retrieval. Preserving1/2 does not grant3. An unsupported attachment must never be silently dropped while reporting the whole user submission succeeded; original selection/paste/send controls need a truthful capability gate. A remote machine's path must not be converted to a local file URL and opened against the viewer's filesystem. No personal file was read or submitted during this review. New transport/path ownership/byte bounds would require an explicit agreed contract, currently pending rather than implemented or accepted.


## Original terminal capability and affected flow gates

Original CrewSessionWindowView SessionRunContentView uses the real SwiftTerm AgentTerminalView for Claude and a structured Codex transcript. Current CrewdWorkspace only reads session.inspect screen (max200 lines) as a projection; remote permitted methods include lifecycle/decision RPCs but no public arbitrary PTY input/resize/stream contract. A text screen projection cannot establish preservation of the original interactive terminal. The client author and root were informed; public contract remains the backend's unique-write architectural decision.

QA's complete affected flow gates, to be applied only when a terminal capability actually freezes:

- Distinguish view/history, input/resize and structured decision authority for the selected real session/runtime identity. Switching crew/machine or revoking a grant cannot retain the old writable handle or expose a foreign terminal. Snapshot readiness alone is not input permission.
- Start one isolated fake interactive PTY, exercise input, resize, streamed output and structured decisions, then Stop to confirmed physical process and ledger termination. Resume retains the intended session/thread and does not invent a second runtime. Existing session Stop evidence is reused outside newly added transport behavior.
- Start a slow or blocked terminal stream, revoke permission or change ownership online, and check no post-revocation unauthorized output/input; cancellation must release only owned subscriptions/requests, preserve writes whose outcome is unknown, and not wait indefinitely for an unresponsive transport.
- Drop the connection after an accepted terminal operation but before its receipt; retain the same immutable request and classify/read status without automatically replaying raw input or starting another model turn. Viewer window closure, explicit app Quit and runtime termination are distinct outcomes.
- For Linux installation, ordinary runner tests use related same-UID prefix process identity/birth plus the managed runtime shared lease across exec and actual child survival; concurrent writers require exclusive lease/CAS. Wrapper death cannot allow a surviving managed child to be overwritten. Unreadable relevant identity must refuse; inaccessible unrelated privileged processes are not a blanket blocker. Unknown installation readback is never an automatic activation retry.

These gates are a test design and unresolved capability inventory, not a feature implementation or accepted terminal/installer module. Actual models, LAN trust, installation and personal data remain outside the isolated fake/source review authorization unless separately established.


## Current unknown-write limits: client identity is not a server receipt

Independent source check distinguishes existing specific create receipts from absent general write status. Document/folder create and selected remote configuration/invite/accept operations have actual requestId/reused contracts; their accepted tests remain reusable. CrewCreateParams and MessagePostParams have no such requestId; there is no public general request-status operation giving crew/message/session writes equivalent server deduplication or per-request recovery. A client-generated UUID cannot supply it.

Current CrewdWorkspace OriginalFirstMessage.id explicitly denotes presentation identity. TextSubmission UUID and CrewdDrafts revision identify local view/snapshot entries; uncertainTextSubmissions is an in-memory collection. The single-scope submission gate blocks another message in the same unknown context and retains the local original payload for inspection, but does not prove server idempotency, positive reconciliation or durability across app restart. Future criteria in this matrix remain desired gates, never assertions these absent APIs already exist.

Focused original-front acceptance at the current contract boundary: an actual post whose response is lost must remain visibly unknown with its original crew/machine/payload; switching selection cannot clear it, move it to another crew or replay it on reconnect. A confirmed not-submitted failure may preserve an editable draft. A genuine success receipt may clear only its unchanged original draft. Reappearing matching text or an optimistic list event is insufficient to prove which unknown request committed. Without an agreed durable status API, app restart and human-assisted reconciliation must honestly expose their unresolved limit; they cannot be labelled exactly-once recovery. Public product/schema decisions remain the backend/root's unique scope.

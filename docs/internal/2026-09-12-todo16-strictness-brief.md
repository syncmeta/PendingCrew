# 人类 Todo #16：群消息的必填字段，「必填」到底是哪一档

<!-- doc-ref-base: 85e1c6e -->

**这一条卡着三件**：#112（群里别发太多细节）、#142（消息要指定接收者）、
#143（折叠标题不要猜）。三件的实现都做完了，**差的只是这一个档位**。

## 你要选的

| | 缺 `summary` / 缺收件人时 | 代价 |
| --- | --- | --- |
| **A 硬闸** | **拒绝发送**，错误信息里给出路 | 账最干净；**改错了全组一起哑**——每个 agent 的每一次发言都走这条路 |
| **B 降级 + 标记** | 照发，但气泡上留可见标记、回执说一句 | 不哑；靠自觉的那一半还在 |
| **C 分类分档**（我倾向） | 「必须有人接」的那几类（`human_todo` / `question` / `blocked`）硬性要求；`ack` / `note` 不要求 | 两头都占；多一层规则要记 |

## 我倾向 C，一条理由

你的痛点是**「给人的消息看不见」**和**「摘要是猜的」**，这两件都集中在「要人接」的那几类上。
`ack`（「收到」）也强制写结论，只是徒增仪式 —— 那种消息本来就该一行。

## 一条硬约束，不管你选哪个

`--mcp-serve` 是**一 session 一进程、长期存活**的。改了 MCP 契约，**在跑的 session
不会生效，直到它被换掉**。所以必须两步：

1. **现在**：加参数、加降级提醒、加渲染，**缺参数一律不失败**。
2. **装版之后**：所有 session 都换到新 helper 了，再把闸收到你选的那一档。

⚠️ **#115 就是这么落的，而第二步至今没做。** 所以这次拍板时请一并说清
**第二步谁做、什么时候做**，否则它会跟 #115 那次一样挂在那儿。

## 今天的一条新证据（支持 C）

`headline` 缺失时，回执现在会**把猜出来的那一行原样摆给作者看**
（`CrewMessageFold.receiptHintIfGuessed`，已在 main）。那实质上就是 B 档，而且
它的 doc comment 写明这是刻意的：「schema 里的说明只在写之前被读到一次，而且多半没读，
真正教得会人的是出错那一刻的那句话」。

**所以 B 档已经有一份现成实现了** —— 选 C 的话，只是把「要人接」的那几类从提醒升到拒收，
不用从零做。

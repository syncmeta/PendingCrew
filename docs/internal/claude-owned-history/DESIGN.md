# Claude managed PTY: owned history and strict manual resume

## Current recovery-disposition design (source c62a85bd, 2026-10-29)

The implemented addition closes a specific gap: after a public Claude resume has an Unknown outcome, reopening must neither silently retry it nor permanently prevent a later, separately confirmed recovery when current physical evidence establishes that no original instance remains. The original outcome is unknowable from that later observation and remains Unknown. The precise consumer shapes and refusal semantics are in the [current contract addition](CONTRACT.md#current-addition-historical-resume-disposition-source-c62a85bd-2026-10-29).

The public capability is `session.claude.recovery`. `session.claude.recoveryInspect {sessionId}` is a read-only projection of existing session, physical birth and public receipt evidence. `session.claude.recoveryResolve` is a typed `command.submit` operation, not a direct mutation RPC or a replacement `session.resume`. The previous frozen design's “three reads/no new capability” statement describes the original history feature, not this addition.

The original actor serializes the target/running check; the original DB owner rechecks the caller and evidence in the committing transaction. A deterministic evidence token binds current runtime, full target, original native ID, directory, receipt bytes, births and prior dispositions. It is only emitted for `eligible`; it is not reusable authority. All known births must be physically gone, and an unreadable birth remains blocking. Foreign-principal blockers are considered without disclosing their IDs. Any incomplete evidence, unresolved admission/dispatch state, or restore-marked original receipt prevents disposition.

The receipt query reads 257 rows solely to detect overflow beyond **256 total candidates**, including qualifying prior dispositions as well as unresolved resume candidates. Overflow returns `evidenceUnavailable` after earlier gates; it never silently authorizes based on a truncated list. No pagination, subset disposition or guessed cleanup is added. This bounded design can refuse a long accumulated history; the current implementation deliberately has no automatic pruning or administrative bypass.

A Human explicitly confirms a fresh inspection. The command must carry the complete original UUID array in inspection order and the exact native identity, target and token. The transaction reserves and commits only the new disposition receipt with `originalOutcome:"unknown"` and `effectsDispatched:false`. It changes no original resume receipt, task, message or frontend journal and invokes no provider or terminal effect. Duplicate lookup/idempotent receipt handling retains existing command identity. Client uncertainty returns to read-only lookup of this new UUID, never an automatic replacement submission.

Durability follows existing receipt semantics. Ordinary Core restart changes the runtime binding but leaves stored committed dispositions valid; returned old Unknown rows can be labelled historical due solely to binding mismatch. Database backup/restore instead marks receipts historical, invalidating disposition coverage and retaining original blockers. Neither copying the backup nor a local client cache can recreate authority. Native ID and principal scope also constrain which dispositions count.

The Swift history panel separates “record disposition without starting” from “resume original session.” It validates the closed wire shapes and correlated committed result, discards failed/stale inspection coverage, and refuses Unknown disposition resubmission. The Workspace resume path obtains fresh inspection and accepts coverage only with `noUnresolvedRequests`, no unresolved rows, exact original UUIDs and unchanged source/target. A legacy entry without an identifiable UUID stays blocked. The server's final executor gate independently rejects any uncovered original Unknown. These complementary checks do not transform old journal entries into acknowledgements or clear them.

Delivery boundary: this design describes implemented Core/client seams, not a successful real-Claude lifecycle, native complete-history reader, physical iPhone/iPad test or every deployed host's version. Existing deterministic protocol/receipt tests and package checks retain their own evidence layer; actual provider restoration must still be verified separately. No Cloud/APNs permission, provider account, new transcript reader, automatic message or resume task is introduced.

## Bounded body retention at the original seal

Add one versioned private metadata value per original managed request, keyed under `claude.managed.observations.v1/<requestUUID>` in the existing meta store. It refers to the original immutable receipt/runtime/prompt; it is not execution authority or a second request ledger. This avoids a new DDL/version solely for observational text. Original Store20 backup/restore already copies metadata and revokes restored runtime authority; a historical snapshot can never reconstruct a live seal. Old20 writers refuse managed resume, so cannot use this optional observation value to bypass the new strict resume gate. Do not invent Store21 without a concrete unsafe writer seam.

At original prepare, retain exact authorized task text separately from the already immutable envelope, within its existing1MiB limit and original preparation transaction. Historical rows without this extra fact expose only exact envelope bytes, explicitly marked as such; no string splitting guesses original task boundaries. Do not invent old missing text or read private files to fill it.

On each valid same runtime/request/prompt Stop, while the original actor owns its serial hook queue and actual automatic/manual/birth authority remains current, store a bounded immutable observation in that same owning transaction. Each observation records monotonically numbered local observation, original promptId, observedAt, source `stopHook`, available/missing body, captured UTF8 bytes, original observed byte count, SHA256 of full observed text when supplied, and truncation/retention reason. Retain at most4 observations/request,256KiB captured/observation,64MiB/session and256MiB/Core. Truncate on UTF8 boundaries; a missing field is missing, not empty successful reply. An empty supplied string remains distinguishable. No logged body, argv, env, export side effect, or private transcript path.

Excess observations update only a bounded omitted-count/latest-observation fact; never overwrite a retained body or attach an old body to a new Stop. When bytes cannot be retained, preserve missing/truncated/retention-limit evidence rather than rejecting a legitimate original task transition or pretending complete content. The already accepted original message/request limits remain unchanged.

Stop remains provisional. Same prompt Stop→real idle_prompt uses the existing managed waiting transition, with the latest original observation identity committed alongside it. Working(false) means waiting only. Further tool/activity/Stop/extra input invalidates the waiting qualification through the original managed_response_resumed/Unknown path, without deleting or rewriting previous body bytes. Reads derive ready only from that exact receipt/prompt/observation plus current live runtime authority; revoked/restored/reopened rows remain historical. No observation claims a native turnId, complete answer, task Done, or APNs delivery.

## Strict manual resume through existing control

Keep the existing public session.resume command envelope, fresh target CAS and original receipt lookup. Add only an internal launch intent distinguishing explicit Human resume from new launch/automatic wake, not a JSON/provider setting or second command ledger. Managed resume requires a canonical UUID recorded by that PCW session's original DbLedger; missing, whitespace-mutated, noncanonical or foreign IDs reject before spawn and retain the record. Agent/automatic wake is not an explicit manual resume.

The ClaudeExecutor's ordinary managed launch still rejects an already-recorded ID. Only the internal exact-resume intent can read/require that same recorded ID and call the driver. Driver managed policy bypasses legacy decide_resume fallback: expected original UUID must match exactly; no bad-ID→New, resume-refused→fresh, pending-body move, or new UUID record. Legacy independent seams retain their old behavior but cannot be reached from the production managed path. Existing managed no-respawn handling remains in force.

Core explicit managed resume clears held bookkeeping without generating the legacy resume note. No initial brief, interrupted-task text, queued old input, resume-note delivery observer or old Unknown is attached. Runtime registration remains the original native birth probe/retirement transaction and fresh ManagedRuntime seal; alive/unreadable old birth refuses. Raw leases and automatic pending authority are not inherited. Each explicit resume atomically captures the existing pending-wake and message upper bounds in the original admission sequence and binds them only to the new runtime birth. All first/tick/Working delivery paths exclude older wake rows without modifying their UUIDs, phase or attempts. The private PreparedSnapshot carries the same automatic-context floor through sampling, capture, rendering and the original CAS; no external parameter or persistent cursor is added. Resume/render alone never advances the read cursor. Actual delivery of a later Human task may use the normal ACK to advance its real new end. Older messages remain readable history, and a Human can explicitly quote them in new text.

ManagedHandle.create already waits for the actual SessionStart guard before returning a launched handle. Strict resume additionally requires the original expected session_id and `source:resume`, not startup/other source. New startup requires source:startup. The8s guard deadline/owned cleanup remains bounded. Rejected resume, wrong ID/source, timeout or disconnect preserves the original control UUID/receipt and old native UUID; no replacement process/task is spawned. Guard installation/readiness is not full native-history completion or task completion. Original public physical outcome remains distinct from these qualifications.

A provider may perform internal work while restoring its own state; this module promises zero new PCW automatic input and no authority from old Unknown, not interception of every native internal action. Existing current-task guard/manual-floor rules remain intact.

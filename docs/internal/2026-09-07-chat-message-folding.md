# 群聊消息折叠（人类 Todo #104）—— 设计与实测依据

## 0. 需求原话与它的读法

> 「现在我就是希望总机长和消息折叠这两个先做好，**因为现在消息太多太乱了**」

4-1 的读法（我采用）：**「乱」不是「长」**。抱怨的是条数占地，不是单条字数。
所以是**默认收起**，不是「把细节段落折起来、散文留着」——后者治的是「长」。

这个区分改掉了我第一版方案的整个形状（第一版是按内容类型折代码块/表格/输出）。

## 1. 三条约束（4-1 给的，逐条落在哪）

| 约束 | 落在哪 | 钉住它的用例 |
|---|---|---|
| 默认收起，不是默认展开 | `CrewMessageFold.fold` 返回非 nil ⇒ 渲染层直接收起 | `test_超过阈值且有粗体结论_折起来并拿粗体当摘要` |
| 收起态要一眼看出这条是什么；**摘要不是截断前 N 字** | 摘要只从作者写下的结论取，取不到就**不折** | `test_没有可当摘要的东西时宁可不折也不截断开头` |
| 注入给 agent 的白板不跟着折 | 折叠只活在 `Sources/Chat`，`HookEmitter` 那条路一个字不改 | `test_折叠只活在渲染层_注入面拿到的仍是全文` |

第 3 条要防的是：我们已经有两道方向相反的截断了，别让折叠长成第三道。

## 2. 摘要从哪来 —— 三级，缺了宁可不折

1. **发送者显式给**（`post_to_crew` 的 `summary`，尚未接线）。最可靠。
2. **推导**：正文**前 3 段**里的第一个粗体，其次第一个 markdown 标题。
   围栏代码块整段剔除 —— 脚本里的 `**` 不是强调、日志里的 `#` 不是标题；
   不剔的话，一条贴了脚本的消息会拿脚本里的字当摘要，等于给它编一个没说过的结论。
3. **都没有 → 不折**，整条摊开。

第 3 条是第二条约束的正身：**截出来的开头常常是「收到，我看看」**——
那种摘要比不折更糟，它让人以为自己已经看过了。

副作用是好的：没写结论的长消息在群里显眼地占着地方，**那是给作者的反馈信号**，
而且规矩的执行者是渲染器，不是记性。

## 3. 实测依据（全机 47 个群、11272 条非空消息）

正文长度：中位 292 字 / 5 行；p75 637 / 11 行；p90 1151 / 23 行；最长 6078 字 / 122 行。
其中 **37.4% ≤120 字**，本来就不需要折。

**「粗体写结论」不是新发明的规矩，是已经存在的写法**（按月，只统计 >120 字的长消息）：

| 月份 | 长消息 | 任意位置有粗体 | 首段有粗体 |
|---|---|---|---|
| 2026-07 | 112 | 22.3% | 11.6% |
| 2026-08 | 6242 | 65.0% | 50.4% |
| 2026-09 | 699 | 65.7% | 49.1% |
| 最近 3 天 | 556 | **75.7%** | 58.8% |

第一个粗体落在第 0 / 1 / 2 段的条数 = 327 / 90 / 4（最近 3 天）——
所以只在**前 3 段**里找；再往后找会捞到正文中段的强调词，那不是摘要。

**阈值是量出来的拐点，不是拍的**：

| 阈值 | 会折 | 其中有摘要可用 | 全群总行数变化 |
|---|---|---|---|
| >4 行 | 50.9% | 73.5% | −77% |
| **>8 行** | **31.6%** | **99.0%** | **−74%** |
| >11 行 | 24.9% | 99.5% | −67% |
| >15 行 | 18.6% | 99.6% | −58% |

`>8` 是「几乎每条要折的都有现成摘要」的拐点：跨过它，`不折` 这个兜底分支
几乎不会触发，界面看起来才是齐的。改 `CrewMessageFold.lineThreshold`
一个常量就换档（人类 Todo #2 在拍 4 / 8 / 15）。

## 4. 先造红

把 `fold` 桩成恒 `nil` 跑了一趟：**`Executed 11 tests, with 12 failures`**，
而三条「不该折」的用例（短消息 / 无摘要 / 围栏里的星号）在桩下**仍然绿**。
既证明尺子会红，也证明它分得清两边。恢复实现后 11/11 绿，全量 2049 / 3 skips / 0 失败。

## 5. 一条踩到的坑：共享工作区里 pbxproj 不是「我的文件」

为了「只提交自己的东西」，我把 `PendingCrew.xcodeproj/project.pbxproj`
`git checkout` 回了 HEAD —— **当场把另一条线（常驻后台）的编译打断了**：
`Sources/Mac/Services/SessionDaemonMain.swift:238: cannot find 'DaemonGracefulShutdown'`。
他们的新文件条目是我 `xcodegen generate` 时顺手带进去的，还原就等于把桥拆了。

规矩：**共用工作区时，还原/提交 pbxproj 之前先看一眼里面有没有别人的名字。**
它是 xcodegen 生成的单一共享文件，谁都不能只提交自己那半 ——
一提交就会引用别人还没提交的源文件，从干净检出构建直接挂。

另一条：判「这个文件到底进没进 target」，`nm` 符号表和 `grep` pbxproj
**我这次都读错了**（Debug 构建真正的代码在 `PendingCrew.debug.dylib` 里，
不在那个 60KB 的启动壳里）。**真正分得清的尺子是往那个文件里塞一个语法错误
再构建** —— 它红了，才证明这个文件真的在编译。

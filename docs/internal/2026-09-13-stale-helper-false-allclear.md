# 「一条未完成都没有」是旧 helper 说的，不是账本说的

<!-- doc-ref-base: 663a68c -->
基准提交：`663a68c`（main，0.1.37 发完）。

## 发生了什么

2026-09-13 07:00 左右，数据目录第 5 次发作期间（已连续 6 小时以上读不出来），
我调了一次 `confirm_todo_sweep`，**显式传的是 `all_done: false`**。回执是：

> 记下了：这本账一条未完成都没有。空闲时不会再提醒你，直到有新条目进来。

**这句话是假的，而且它的假法正是这套东西最危险的那种**：账本此刻一个字都读不出来，
所以「读到 0 条」和「一条都没有」在旧代码里长得一模一样；而这条路的收尾动作是
**把那个唯一还在报信的提醒关掉**。

## 为什么仓库里明明修过

修过，而且修得对。`Sources/Mcp/McpServer.swift` 的 `confirm_todo_sweep` 分支现在走
`todos.read` 的三态，读不出来时直接拒：

    case .unreadable:
        return toolResult(id: id, text:
            "ERROR: 这本账这次读不出来，**这次核账没有记下**…")

那笔是 `c46a806`（fix(mcp): 账读不出来时 confirm_todo_sweep 不许把提醒关掉），
`git tag --contains` 显示它**最早进的是 v0.1.35**。

**而这台机器上装着的是 0.1.34。**

## 这一条的价值不在「又发现一个 bug」

没有新 bug。有价值的是这三句的组合：

1. **「修在 main 上」和「跑在机器上」是两件事**，而它们在回执里长得一样 ——
   回执不会说「我是旧二进制」，它只会照旧行为回你一句听着很正常的话。
2. **这次是一份现成的活体对照**：同一个工具，同一本读不出来的账，旧二进制说
   「没事了」，新二进制说「这次没记下」。不需要造实验。
3. 所以凡是「我调了某个工具、它说 OK」的结论，**在装上新版之前都要先问一句
   「这条 OK 是哪个二进制说的」**。

相关：`docs/internal/2026-09-11-stale-helper-toolset.md`（同一个病的另一处），
以及仓库记忆里那条 [[reply_to 的自动 @]]（也是「仓库已修、旧 helper 上不生效、
回执照回成功」）。

## 边界

- 我**没有**去核这句假 OK 有没有真的把提醒关掉。观测到的是：提醒此后照常按最短
  间隔继续来。所以「它没关成」是**观察**，不是我读代码确认的机制。
- 0.1.37 已发布（含这条修复）。这台机器升上去之前，上面那句回执还会照旧出现。

# 装了新版，正在跑的 session 拿不到新工具 —— 三条候选的实测读数

- 日期：2026-09-11
- 起因：人类当面点名。原话「更新难道不会更新工具这些东西吗？这个问题你想办法解决」
- 状态：**①（让它说实话）已实现并合入**；**②（真修）只出方案，等机长过目**
- 实现：`Sources/Mcp/HelperBuildWatch.swift`（commit `ceadc40` / `3814d9c`）

---

## 0. 一句话

**机长倾向的 C 不成立，而且它的前提正好是反的** —— daemon 不是「随 app 一起更新的那个」，
**它是全机最旧的那个进程**。今天量到：磁盘上 0.1.32，活着的 daemon 是 **0.1.27**，
已经连续活了 3 天 19 小时、跨过至少两次装版。

三条里今天真正立得住的只有 **B**，而 B 还可以做得更好：**不必挑时机，让它在每一轮结束时自己换代**。

## 2. 一条仓库里写着、但今天已经是假的话

`Sources/Mac/LocalRunner/LocalSessionLaunch.swift` 的注释里写着（2026-09-08 加的）：

> 装新版本身会重起后台、打断所有 session，而 session 不跨 app 重启存活。……
> 安全时刻就是改动发出去之后的第一次装版之后 —— 那一刻不存在「还有几个老 helper 挂着」
> 的长尾，它们全被那次重启带走了。**这是一个我们自己按得下去的开关。**

**这句话在写下的那天是对的，今天是假的。** 差别是 **2026-09-04 把默认后端翻成了
daemon**：session 从此由常驻后台养，**装 app 不再打断它们** —— 那正是前后端分离的
全部目的。于是「装版会把老 helper 全带走」这个副作用**跟着一起没了**，而注释没跟着改。

上面第 1 节的 16/23 就是这句话失效的直接证据。**这不是「文档写错了」，是「描述会变的事实
的静态文字过期了」** —— 而它比没写更危险：机长正是按「装版即收口」在排时间点。

（已在同一批改动里把这段注释改成现在成立的说法。）

## 3. 三条候选，逐条核

### A：helper 自己重启（re-exec）

**前半截成立、而且很便宜。** `McpServer` 在内存里几乎不存状态 —— 白板游标、续跑租约、
Todo 全在磁盘上。helper 随时可以对自己 `execv` 一次，pid 不变、stdin/stdout 不变，
对面（claude）看不出发生过什么。

**后半截不成立，卡在客户端。** 换了新进程也没用 —— **claude 手里的工具表还是老的**，
它不会再问一次。MCP 协议留了一条路（服务端发 `notifications/tools/list_changed`，
客户端重新 `tools/list`），但本机 claude **2.1.268** 的客户端是这样建的：

```js
listChanged: {
  tools:     { autoRefresh: false, debounceMs: 0, onChanged: () => {} },
  ...
}
```

**自动刷新关着，回调是个空函数。** 通知会被收下，然后什么都不做。

> **这一条是「读代码读到的」，不是「实测到的」** —— 我读的是 claude 二进制里那段
> 客户端构造代码（白纸黑字，可复核：`strings ~/.local/share/claude/versions/2.1.268`
> 搜 `autoRefresh`）。**没有端到端跑过一次真的通知。** 要把它升成实测，得造一个会发
> 那条通知的 MCP server 挂上去看。

**结论**：单靠 A 不解决问题，而且那半截的开关**不在我们手里**（claude 升个版就可能变，
两个方向都可能）。**不建议把方案压在它身上。**

### B：session 级重启（`--resume`）

**今天就成立，而且零件全是现成的。**

- daemon 就是 claude 的亲爹（实测：22 个 `claude` 进程的 ppid 全是 15229）。
- `--resume <会话号>` 已经在用（`Sources/Mac/LocalRunner/SessionConfig.swift:144`），重启不丢上下文。
- 单个成员的重启入口也已经有（`Sources/Mac/Services/CrewSessionRunner.swift:2495` `restartMember`）。
- **新起的 claude 会按固定路径现 spawn 一个新 helper** —— 那个路径上的文件已经是新版，
  所以新 helper 的工具表一定是新的。**这一步不需要 daemon 自己是新的。**

**代价**：当前回合会断。

### C：helper 不再自带工具表，改成向 daemon 要

**前提为假，而且是反着的。** 机长写的是「daemon 是随 app 一起更新的那个」——
实测：daemon 0.1.27，磁盘 0.1.32，**它比任何一个 helper 都老**。

**为什么它不换代，是设计使然，不是 bug**：daemon 存在的全部意义就是「更新 app 不打断
session」。要让它跟着装版换代，就得先解决「怎么在不杀死 22 个 session 的前提下换掉养着
它们的那个进程」—— **那是同一个问题的更难版本**，不是它的解。

仓库里也**没有**「daemon 比 app 旧就换代」的代码（grep 过）。设计文档
`docs/internal/2026-08-19-backend-split-design.md` 的验收项 A1 第③条写着「等空闲自动换代」，
**那条没实现**。（该文档声明的基准提交是 `7065048`，已落后 main **617 笔** —— 基准本身
有效，但很旧，别拿它当今天的现状读。）

**还有一层，比前提更要命**：C 只搬「工具表」。**一个新工具不只是一张表，它是一段代码** ——
老 helper 就算拿到了新表，`tools/call` 打进来还是没人接。真要 C 成立，helper 得退化成
**一个纯转发壳**，每一次调用都转给 daemon 执行。那是一次真正的前后端再分家（helper 现在
只碰共享文件，**跟 daemon 之间一条通道都没有**），并且把所有 crew 工具的执行搬到 daemon 上。

**结论**：C 不是「真修」，**它是把同一个洞挪到一个活得更久的进程上**，代价还大一个量级。

## 4. 建议：B+ ——「每一轮结束时自己换代」

B 的代价是「当前回合会断」。**这个代价可以不付** —— 因为我们手上恰好有一条**永远是新代码**的腿：

`--mcp-turn-hook`（回合结束 Stop hook）跟 `--mcp-hook` 一样**每次现 spawn**，
文件一换掉它下一次就是新代码。**一个 session 的回合刚结束那一刻，正是重启它的零代价时刻。**

所以：

1. 装新版之后，**谁都不动**。在跑的 session 照常跑完手上的活。
2. 每一轮结束时，那个**新代码的** turn hook 顺手比一次「我这个 session 的 helper 比磁盘旧吗」
   （判定就是 ① 里已经写好的 `HelperBuildWatch`，纯函数，直接复用）。
3. 旧了 → 往控制通道写一条「请把我 `--resume` 重起一次」。
4. daemon 排空控制通道时执行 —— 这是它已经在做的事。

**效果**：装完版之后，**每个 session 在它自己的下一个自然停顿点换代**，没有任何一轮被打断，
也不需要人去挑时机。忙的 session 晚一点换，闲的马上换 —— 正好是想要的顺序。

**代价与风险，说清楚**：

- **一次多余的进程重启**（每个 session 一次，只在装版后）。claude 冷启大约几秒。
- **`--resume` 不是免费的**：它重放上下文，会吃一次 token。密集装版时这笔不小。
  → 建议加节流：同一个 session 一天最多自动换代 N 次。
- **鸡生蛋**：第 4 步那段策略代码住在 daemon 里，**而 daemon 正是最不换代的那个**。
  所以这套东西要生效，**daemon 必须先被换掉一次**（今天只能人手来：`--daemon-stop` 再重开）。
  这一条必须写进发版说明，否则会出现「代码合了、行为没变」，而那种失效最安静。
- **daemon 自己的换代仍然没解**。它是独立一件事，比这件大。本方案不假装解决了它，
  只是把它从「所有问题的前提」降级成「一件单独排期的事」。

# 侧栏「藏起来一个 crew」—— 决策记录

日期：2026-08-26 · 版本：0.1.16 的组成部分 · 状态：已实现（手动这一半）

人类原话就一个词：**藏起来**。语义 = **从侧栏消失，聊天记录留着，不真删**。

这份文档记的不是怎么实现的（代码里有），是**三条当时拐了弯的决策**，以及那条**没
有走的路**为什么没走。后两件删掉比留着省事，但下一个人会为此重新推一遍。

---

## 一、没走的那条路：「空群自动判定」

### 判据当时是怎么定的

需求最早被说成「**空群**解散」。落到可执行的判据是三条与：

1. **零 session** —— 这个 crew 从来没起过 session；
2. **无实质消息** —— 白板上除了系统行以外没有真正的对话；
3. **建群超 24h** —— 刚建出来还没来得及用的不算。

### 实测结果（2026-08-26，全机）

**本机 42 个 crew，按上面三条判空，命中 0 个。**

拆开看：

| 切面 | 数量 | 明细 |
|---|---|---|
| 从没起过 session | 7 | 但它们**全都有真实对话**：`神秘弹窗溯源` 14 条、`Changyon` 10 条、`跨机与Workspace` 8 条、`iPod灯控` 8 条、`Brick` 4 条 |
| 实质消息 ≤3 条 | 2 | |
| 三条全中（= 判定为「空」） | **0** | |

### 结论：判据瞄准了一类在这台机器上不存在的对象

人类想从侧栏清掉的**不是「空」的群，是「完事了 / 不需要再看见」的群** —— 而那些
群恰恰**消息最多**。按「空」自动判定，永远抓不到人类真正想清掉的那一批。

所以裁决是：**手动藏是主功能，自动判定不做。**

**不是推迟，是先不做。** 等看到人类实际藏了哪些群，再从真实行为反推判据 —— 那时
判据多半也不是「空」，而是**「多久没动静」**。`manuallyHiddenAt` 这个字段名就是为
那一天留的位置（见下一节）。

**留档不删的理由**：下一个要做自动判定的人，看到这一页就知道这条路当初为什么没走，
不必重新量一遍，也不会以为是漏掉的。

## 二、为什么存 `manuallyHiddenAt` 而不是 `hidden`

将来若真加了自动判定，「人自己藏的」和「程序判定该藏的」是两件事：人藏的那些绝不
能被自动逻辑取回，自动藏的那些应该能被一句「别这么干」批量撤销。**两种语义挤在同
一个布尔值里就再也分不开了** —— 而那时已经有存量数据，分不开就永远分不开。

字段名从第一天起写死「这是人手动藏的」，成本是零，收益是那一天不用做数据迁移。

**存法是两个字段，各归各的账本**：

| | 存哪 | 是什么 |
|---|---|---|
| `LocalCrew.manuallyHiddenAt` | `local-crews.json` | 藏的**那个时刻**。crew 自己的属性。 |
| `CrewViewedStore`（crew 级 lastViewed） | UserDefaults | 「**这台机器上这个人**看到哪儿了」。不是 crew 的属性，不该混进组织事实里。 |

第二个照 `SessionUnreadStore` 那条现成的路子建 —— 那是 session 级的同一件事，同样
存 UserDefaults、同样不进持久数据。

未读 = **末条消息时间 > max(manuallyHiddenAt, lastViewed)**。

为什么要第二个字段：藏起来 ≠ 不再关心。人会点进去看看有没有动静，**看完那个提示就
该消失**；一个不可信的计数比没有计数糟。而 `manuallyHiddenAt` 必须保持「只是藏的
时刻」这一个含义 —— 拿它当已读水位刷新，字段名就开始撒谎了。

### 一条不许踩的（**不是新债，是已在案的那一笔**）

侧栏这条路算未读**只准读 `CrewStore.lastWhiteboardMessages` 那份后台按指纹门控算好
的快照，比时间戳**。`SessionUnreadStore.unreadCount` 里那句
`whiteboard.list(crewId:)` 是解整板 JSON，它活得下去是因为只作用于当前打开的那一个
session；侧栏是几十个 crew × 每次重绘，照抄它就是 2026-08-17「开久了卡」的完整复现。

那处全量读**已经在案**：`CONTRIBUTING.md` 第 3 条点名的
`CrewSessionWindowView.badgeCount(for:)` 就是它。**这里不新开一笔债** —— 同一笔债写
三处，将来有人修好了只销掉一处，剩下两处继续挂着，下一个人看到就以为还有别的洞
没修。

## 三、子 crew：选了「拦住」，明确否决「藏父提子」

### 被否决的做法：藏父、把子 crew 提升到顶层显示

那会让侧栏显示的组织架构和实际汇报线**对不上** —— 人看到的树是假的。宁可留一个空
父在那儿，也别让组织图撒谎。

这条不只是取舍，它决定了可见性的**算法形状**：不能把被藏的那一行从数组里滤掉。
`CrewDAGTreeView` 把「父不在本组」的 crew 当根渲染，滤掉父等于把子提到顶层 ——
正好撞在这条否决上。所以 `CrewHiding` 做的是一次**自根向下的可达性**：自己被藏 →
不可见且不再往下传播；有父边时至少要有一个可见的父。

（多父 crew 只要还有一条露着的入口就仍然看得见 —— 它确实还进得去。）

### 在「拦住」和「连子树一起藏」之间选了什么

**底下有子 crew 正在跑 → 拦住**，点名是哪几个，说明为什么。

理由：藏的语义是「这事完了、不需要再看见」，而底下有 session 在跑恰恰说明**没完**。
一次右键就把一整棵还在干活的子树从侧栏抹掉，人下一秒想去看那个正在跑的子 crew 会
找不到入口 —— 这跟「删了」在体感上没有区别。拦住只让人多做一步（先停掉、或先把子
各自藏起来），而且理由当场说得清。

**子 crew 全闲着 → 放行**，但落地前确认一下，说明它们会跟着一起消失、不会被提到
顶层、取回父时一起回来。

判定不看「有没有子」，看的是**「藏了这一下，哪些此刻可见的 crew 会消失」**：活跃的
子若还挂在另一个可见的父下面，它并不会消失，那就不该拦。

## 四、边界：藏是人类界面的概念，不是组织结构的改变

藏了的 crew 里的 session **照常干活、照常收发消息**。`directory` / `contact` / 每轮
注入的组织树、MCP 工具、白板投递，一律不受影响。这次只动 macOS 侧栏这条 UI 路。

一致性上有一处容易漏：侧栏有**两种视图**（层级 + 时间流，Todo #50），过滤加在侧栏
那一层、两种视图喂同一份 `visibleCrews`。只改一种、另一种漏掉，是这类改动最容易翻
的车。

# 侧栏那一行显示什么 —— #145 动手前的四个读数

基准提交：`272282d`（本机 main，2026-09-12）。数据面：本机
`~/Library/Application Support/PendingCrew/`，52 本白板、13592 条消息。

人类 Todo #145 的原话：「总机长每次排序的时候 就总结一下每个机组的摘要显示在最新
消息那个位置。再给个手动刷新按钮，手动出发让总机长重新总结、排序」。

动手前量了四件。**其中两件把这条需求的前提改掉了**，所以先写在这儿，再谈怎么做。

## ① 「最新消息那个位置」有三处，只有一处已经改过

| 视图 | 那一行显示什么 | 出处 |
| --- | --- | --- |
| 层级 | 最后一条消息的开头 | `CrewSidebarCrewRow.preview(of:)`（不传 `statusLine` → nil） |
| 时间流 | 同上 | 同上 |
| 总机长 | **机长自己报的那句状态** | `CrewChiefListView.swift:96` 传 `statusLine` |

所以「最新消息那个位置」在两个老视图里仍是原样，只有第三个视图换过。
要改哪个（或三个都改）是产品决定，不是实现细节。

## ② 排序这个触发点**全史 0 次**

`arrange_crews` 是机长手动调的 MCP 工具，**没有任何定时器**。

精确匹配它两条回执原文（`"个 crew 顶到了侧栏最前"` / `"撤掉了侧栏排布"`）扫全部
白板：**0 命中**。`crew-arrangement.json` 不存在。

> 扫描器自身的对照：同一趟扫到 52 本白板、13592 条消息，对照串命中 4071 条 ——
> 报 0 不是因为扫描面是空的。

**所以「每次排序的时候就总结一下」挂在一个从未触发过的事件上。**
原本担心的「很频繁 → 每次一轮 LLM → 很贵」不成立，真正的问题是它根本不触发。

根因链：总机组那条记录 `workingDirectory` 为 nil → `CrewSessionRunner` 的
`:2347` / `:2462` / `:2078` / `:2509` 四处同一道 guard 全部抛
`captainNoWorkingDirectory` → **总机组起不了任何 session** → 没有总机长 →
没人排序、也没人写摘要。

## ③ 已有的那半（#136）在实践中基本没被用

「机长自报状态」这套（`crewStatus` 字段 + 读侧规则 + 侧栏那一行）确实已经落地。
但量下来：

- **50 个 crew 里只有 2 个曾经填过**，其中一个已经 50 小时没更新。
- 另外 48 个从来没填过 → 总机长视图里那一列**现在是 48 行「还没有」**
  （`CrewStatusLine.make` 在 `resolved == nil` 时返回 `Line(text: "还没有")`）。

**这条最值得注意**：那个机制不是坏了，是**它依赖每个机长自觉去填，而 96% 的机长
从不填**。人类看到的「一列还没有」，很可能正是他提 #145 的原因。

而这恰好是 #145 的方案**更可靠**的理由：它把「谁来写这句话」从 47 个自觉的机长
收敛成 1 个总机长。**别把 #145 当成 #136 的重复 —— 它们的作者不同，而作者是关键。**

## ④ 总机组现在在人类机器上什么样

0.1.34（二进制时间 2026-09-12 00:11）。名册 49 条里有它：
`title=总机组`、`captainName=总机长`、`crewNumber` 为空（「内建那一层不占通讯录号」
那个修正生效了）、无父边、`sessionMembers` 0 个。
群聊文件 `whiteboards/pendingcrew-chief.json` **还不存在**（懒创建，第一条消息才生）。

所以他现在看得见入口、点进去是一个空群聊 —— 跟设计一致，不是故障。

## 边界

- 以上全是**读代码 + 读本机数据目录**。**没有一条是在跑起来的界面上目视过的**。
- ③ 那两个数是**这台机器**的，不是普遍规律。换一台机器、或者哪天大家养成了填的
  习惯，结论就变 —— 引用它之前请重新量，别传这两个绝对数。
- ② 的 0 次是「全史没有痕迹」。它证明不了「将来也不会频繁」——
  一旦总机长真跑起来并养成排序习惯，成本问题会回来，那时要重新量。

# 空闲核账提醒还在按最短间隔打人 —— 修好了，但没装上

基准提交：`e37af32`（写这份时我这条线的 main HEAD）。

## 现象

故障窗口里，「你停下来了，但这本 Todo 账这次读不出来」按**最短间隔**反复问。
`10f665f` 正是为此而修：地板间隔的输入（`lastRemindedAt`）跟被守的那本账
同一个基座、一起坏掉，于是那道闸在唯一需要它的场合失效。

## 为什么修了还在打

那条提醒由 `CrewSessionRunner`（app 进程）产出，不是 helper。
所以 `10f665f` 那份进程内退路本该活得够久 —— **但它不在正在跑的那个二进制里**。

| 读数 | 值 |
| --- | --- |
| `/Applications/PendingCrew.app` 二进制 mtime | 2026-09-12 00:11:08 |
| 正在跑的进程启动时刻 | 2026-09-12 00:11:10 |
| 装着的版本 | 0.1.34 (20707.55457) |
| `10f665f` 提交时刻 | 2026-09-12 11:29:10 |

装着的这个比修好那一刻早 **11 小时 18 分**。代码在 main 上，人机上跑的不是它。

这是本仓那条老规矩的又一次现场：**装版就是收口点**。
`--mcp-hook` 每次工具调用都重新起进程、立刻吃到新二进制；
而这条提醒长在 app 进程里，app 不重装就永远是老的。

## 还有一层，不是缺陷

新二进制装上之后，故障窗口里提醒**仍然会来**，只是退回地板间隔而不是最短间隔。
因为 `row()` 的退路只把「上次提醒时刻」记进程内，**确认本身仍然保守当成没有** ——
读不出账的时候不该替它宣布干净。这是对的，别去「优化」掉。

## 所以

要停掉这个循环，唯一的动作是**装一个 `10f665f` 之后的构建**。
而 0.1.35 此刻卡在公证（父账人类 Todo #17），所以这件事不是我这条线能推的。

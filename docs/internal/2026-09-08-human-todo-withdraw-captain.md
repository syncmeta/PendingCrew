# 撤不掉的人类 Todo：把一个永久权限从「会消失的 session」搬到「常驻的机长」

- 日期：2026-09-08
- 触发：人类原话 —— 「我希望机长能处理所有的 todo，不要出现这种撤不掉的情况。」
- 现场：子 crew「协作系统规划」有两条人类 Todo（#3 / #4）已被人当面拍板作废，
  **谁也撤不掉**：提出它们的 session 已经不存在了。同一天机长自己也撞过同一堵墙。

## 根因

`LocalTodoStore.withdrawObstacle` 的所有权闸：

```swift
guard let owner = item.createdBySessionId, owner == sessionId else {
    return .notYours(owner: item.createdBySenderName)
}
```

判据是「你是不是提出者」，而提出者被表示成一个 **session id**。

**session 是会消失的实体** —— 后台重启、正常收工、被停掉都会带走它，这是常态不是异常。
把一条**永久性的权限**挂在一个会消失的东西上，就是这个 bug 的形状本身。

由此至少三类条目永远撤不掉，而且**没有任何出口**：

| 类型 | 死在哪一句 | 今天有没有真发生 |
|---|---|---|
| ① 提出者 session 已消失 | `owner == sessionId` 判等不成立 | **有**（#3 / #4，以及机长自己那次） |
| ② `createdBySessionId` 根本没记的老条目（字段是后加的） | `guard let owner` 解包不成立 | 代码上必然，今天没抓到实例 |
| ③ 由别人代提的 | `owner == sessionId` 判等不成立 | 未观测 |

后果不是「不方便」：那两条会**一直在人的待办列表里亮着灯**，催他回答一个他今天
已经当面回答过的问题。而旧回执给出的唯一建议是「提出者已经不在了就在群里说明，
让人类自己决定删不删」—— **那正是把死条目永远留在人账上的那条路**。

## 口径（机长拍板）

**机长身份 ⇒ 撤得动本 crew 的任何一条人类 Todo。**
判据从「你是不是提出者」换成「你是不是这个 crew 的机长」。

理由：**机长是常驻角色**。这个 session 没了，crew 还有机长；子 crew 换了机长，
新机长照样撤得动 —— 问题就已经解决了。

边界，一条都没放宽：

- **不跨 crew**。父 crew 机长撤不了子 crew 的（那会绕过人家自己的机长）。
  实现上这条根本不需要新代码把关：`withdrawObstacle` 看不见 crew，
  真正的边界在调用方 —— `withdraw(crewId:)` 和 MCP 那层的 `crewId`
  都是本 session 那**一个**，机长伸不出去。
- **撤回仍然不是删除**。条目留在列表里、原因写进它自己的时间线、群里出一行
  「撤回 人类 To Do #N：…」、人不同意能追问把它问回来。一个字没动。
- **`delete` / `dismissed` 一个字没碰**。那两条是人类自己的动作。

## 改了什么

1. `LocalTodoStore.withdrawObstacle(item:sessionId:isCaptain:)` —— 新增判据。
   `isCaptain` 默认 `false`，默认值刻意选在**收紧**那一侧：新调用点漏传只会让机长
   少一项权限（不方便），不会让谁多出一项权限（伤人）。
2. `LocalTodoStore.withdraw(...)` 透传。
3. `McpServer` 两个调用点都接上 `isCaptain` —— `withdraw_human_todo` 和
   `add_human_todo(supersedes:)`。**两扇门共用同一份判据**，只接一扇会让同一个人
   在两扇门上得到相反的答案。
4. **文案**（这一条和代码一样要紧，agent 只读得到文案）：
   - 工具描述从「撤回**你自己提的**那条」改成写清两种资格，并点明
     「机长是常驻角色、session 会消失，所以这本账的清理责任在机长身上」。
   - 撤不动时的回执，出口从「让人类自己决定删不删」改成「找本 crew 的机长」。

## 变异自证（8 次，逐条）

规矩：**「删掉被测项不红」说明它压根没被测到** —— 链上更早的短路会挡住它，
而且伪装成「全绿」（见 `docs/tech-debt.md` 里 2026-09-07 那条）。

| 变异 | 预期 | 实测 |
|---|---|---|
| M1 机长只放开「没记提出者」那一支 | ① 那条红、② 那条绿 | ✅ 正如预期 |
| M2 机长只放开「记了但对不上」那一支 | ② 红、① 绿 | ✅ |
| M3 整条修复删掉（`if true`） | ①② 都红 | ✅ |
| M4 `withdraw_human_todo` 不接机长标记 | MCP 那条红 | ✅（只红它一个用例） |
| M5 `supersedes` 那扇门不接机长标记 | supersede 那条红 | ✅（只红它一个用例） |
| M6 放宽给所有人（`if false`） | 「不许放宽」的守卫红 | ✅ 红了 8 个用例：改动前就有的 5 个 + 这次新加的 3 个 |
| M7 机长绕过「人类已删」 | 应该红 | ❌ **没红** |
| M8 机长绕过「已经撤过」 | 应该红 | ✅ |

**M7 就是那个陷阱，当场又踩了一次。**
`testCaptainCannotWithdrawWhatTheHumanDeleted` 走的是 `withdraw`，而 `withdraw` 里
`liveIndexLocked` **更早一步**就找不到已删的行、直接返回 `.notFound` —— 判据里那句
`!item.isDeleted` 对机长放开与否，它一点都感觉不到。那条测试**测的不是它自称在测的东西**。

补法是绕开那条链、直接把已删条目递给判据
（`testCaptaincyDoesNotResurrectAHumanDeletedItemInTheJudgeItself`），并在原测试上
写清「它挡住的不是判据」。补完 M7b 当场红。

## 没能覆盖的、以及这个改动让什么变得可能了

### 我**没能**做到的

- **现场没清干净。**「协作系统规划」的 #3 / #4 我撤不掉，而且**不是权限问题，是版本问题**：
  MCP helper 就是 app 自己的二进制（`Bundle.main.executablePath` re-exec），
  所以这个修复要等**新版 PendingCrew 装上、session 重起**之后才存在。
  在那之前，那两条只能由人类自己在面板上删掉。
  跨 crew 又是刻意不做的，所以我这个 session 无论如何都伸不过去 —— 那件事得由
  「协作系统规划」的机长在新版上做。
- **类型 ③（别人代提）没有独立的红。** 它和类型 ① 在代码上是同一句判等，
  单独造一条只会得到一条「删掉被测项也不红」的假覆盖。这里如实说：它被覆盖了，
  但覆盖它的是类型 ① 那条测试。
- **`isCaptain` 的真实性没有被这一层验证。** 它来自 helper 的 `--captain` flag，
  跟仓库里其它机长专用工具（`plan_add` / `answer_decision` / `crew_ordering_signals`）
  用的是同一个来源、同一道闸。谁能伪造这个 flag，谁就能伪造那几个 —— 这一单没有
  把那个面变好，也没有把它变坏。
- **没有跑真 app**。全部是单测层面的验证；菜单/面板上没有撤回入口，所以也没有
  可看的 UI 变化。

### 权限放宽了，最坏情况下谁能拿它干什么

**一个 crew 的机长可以把本 crew 里任何一条还没被回答的人类 Todo 从人的待办里拿走。**
包括别的 session 提的、包括提出者还活着的。

为什么可以接受：

1. **它不是删除。** 条目留在列表里、撤回原因落在它自己的时间线上、群里有一行带原因的
   播报、`withdrawnBySessionId` 记着是谁撤的。人回头看得见发生过什么，也能在那条上
   回一句把 agent 叫回来。这次改动一个字都没动这几条（有测试钉着）。
   **一句边界**：撤回标记不会被人的回应清掉 —— 那条不会重新亮起黄点，
   它是「不再自动催你」，不是「被冻起来了」。这是撤回原本的设计，不是这次改出来的。
2. **它有天花板。** 就是本 crew，而且撤不掉人类已经删掉的、也撤不了两次、
   原因仍然必填。
3. **它的反面更贵。** 不放宽的代价今天已经量到了：两条死条目永远挂在人的账上，
   而且**没有任何出口**。把「可能被误撤、但留痕、可追问」换掉
   「必然撤不掉、且无声地一直催人」，是划算的。

真正的残余风险是**误撤**（机长判断错了那件事还没作废），而不是恶意。挡它的是留痕和
可追问，不是权限 —— 所以工具描述里补了一句「替别人撤之前先确认那件事**真的**不成立了」。

2026-09-08 19:44，机长（captain-0a5860fb）在故障当口量的。
**这是 `docs/internal/2026-09-08-ledger-read-failure-diagnosis.md` 里那个
「没能复现、EPERM 到底谁发的仍然不知道」的现场。**

## 一、实测到的（都在故障当口）

```
读 ~/Library/Application Support/PendingCrew/ 下任意文件  → errno=1 EPERM
  · <crew>.todos.json      EPERM
  · <crew>.json (白板)      EPERM

  · listdir(whiteboards) → 能，2628 个条目

```

**形状：元数据放行、内容拦截，且只针对 PendingCrew 的数据目录。**
不是权限位（0644、属主是自己），不是文件缺失（stat 有 size），
不是整个 home 不可读（对照组 OK）。

## 二、一个**已被后续证据削弱**的成因假设（进程时间线）

```
/Applications/PendingCrew.app/Contents/MacOS/PendingCrew  被替换于  19:04:01
新 GUI      pid 12177   起于 19:04:03      ← Sparkle 更新后重启了界面
daemon      pid 15229   起于 09-07 22:02   ← **早于替换 22 小时，没有被重启**
我这条链：  bash → claude(23126, 08:43) → daemon(15229)
```

**Sparkle 自动更新换掉了磁盘上的可执行文件，重启了 GUI，但没有重启 daemon。**
daemon 仍在运行那份**已经被替换掉的**二进制。macOS 对「运行中进程的可执行
文件已与磁盘不符」会作废其 TCC 授权 —— 于是**整条 daemon 谱系**（daemon 自己、
它的 agent 子进程、以及那些 `--mcp-serve` helper）读不了 app 自己的数据目录。

新 GUI 跑的是新二进制、授权是新的，所以它照常读写（`crew-sessions.json`
mtime 19:44 就是它写的）。

**这解释了那个 worker 留下的问题**：他写过
> 痕迹文件里的 `argv=` 一句话就能回答「是 agent 谱系被拒还是 app 自己也读不动」
> —— 这两个是不同的病。

**答案：是 agent 谱系被拒，app 自己没事。**

也解释了间歇性：**每次 app 自动更新之后、daemon 重启之前，这个窗口里所有
agent 都是哑的。** 之前那 11 次里有 2 次落在「休眠唤醒那一秒」，可能是同族
（唤醒后 code signature 复核）——**这条没验，别当结论。**

### ⚠️ 20:00 更新：上面那个假设至少不完整 —— 故障自己好了

19:44 写入被拒；**19:5x 再试，成功了，没有重启任何进程。**
子 crew「驾驶舱改造」那边也是间歇的（同一分钟内 human-todos 先成功、后失败）。

**「运行中进程的可执行文件被换掉导致 TCC 授权作废」是持续性的** ——
它不会在没有重启的情况下自己恢复。所以：

- **那个假设解释不了间歇性，不能当结论。** 它现在的地位是「一个和时间线吻合、
  但被自恢复现象证伪了单向性的猜想」。
- 间歇性这个事实**排除了**一整类解释：任何「一次性作废、直到重启才恢复」的机制
  （TCC 撤销、签名失效、句柄永久失效）都不成立。
- 它**指向**某种瞬时性的东西（竞态、资源耗尽、某个短暂持有的排他状态），
  **但我没有证据指认是哪一种，不猜。**

**我在这份文档第一版里把这个假设写进了标题**，虽然第五节标了「是推的」——
标题的份量远大于第五节。这是「把推测写成结论」的又一次，记在这儿。

## 四、修法与遗留

**当场修法：完全退出 PendingCrew 再打开**（重启 daemon）。它会中断所有 session，
但那正是拿回授权的唯一途径。

**该修的产品缺陷（按要紧程度）**：
1. **自动更新后 daemon 必须重启**，或者至少要检测到「我的二进制已被换掉」并
   大声报出来。现在它安静地变哑。
2. **`post_to_crew` 在这段窗口里回过「已发到」而消息没落盘。** fail-loud 那条
   路径显然存在（19:44 那次就报对了），但更早那几次没报 —— 要查清是哪条分支
   吞了它。
3. **痕迹文件放在被保护的目录里，故障时自己也读不出来。** 它解决了「播报被吞」，
   没解决「查的人读不到痕迹」。考虑挪到不受 TCC 保护的位置（如 `~/Library/Logs/`）。

## 五、边界

- 「macOS 因可执行文件被替换而作废 TCC 授权」是**从时间线和现象推出来的**，
  没有直接观测到系统的授权撤销事件。要坐实需要看 TCC 日志或造一次实验
  （替换二进制但不重启进程，再读）。
- 19:13–19:44 之间**哪几条消息真的丢了**，没有逐条核对。
- 那 2/11 落在休眠唤醒的旧线索与本次是否同族，**未验**。
- **故障为什么会自己恢复，完全不知道。** 恢复的那一刻我没有在量别的东西，
  所以「恢复时发生了什么」这一栏是空的 —— 下次再遇到，那才是最该抓的一秒。

### 最锐利的一组：**按操作分，不按文件分**

在**同一个目录**里，同一个进程，同一秒：

| 操作 | 结果 |
|---|---|
| `getdirentries`（`ls` 目录，2644 项） | **允许** |
| `stat`（读元数据） | **允许** |
| `open(O_WRONLY\|O_CREAT\|O_TRUNC)`（`echo hi > 新文件`） | **允许** |
| `unlink`（删掉它） | **允许** |
| `open(O_RDONLY)` 读**我自己刚建的那个文件** | **EPERM** |
| `open(O_WRONLY\|O_APPEND)` 追写**我自己刚建的那个文件** | **EPERM** |
| `open(O_WRONLY\|O_APPEND)` 已有文件 | **EPERM** |

**这一条推翻了两个此前很自然的假设**：

1. **不是「已有文件 vs 新文件」** —— 我自己刚建出来的文件，回头读也 EPERM。
   所以跟文件来历、inode、扩展属性都无关。
2. **不是「读被禁、写被允许」** —— 追加写同样 EPERM。允许的只有
   「整份创建/覆盖」和「删除」。

**允许集 = {列目录, 取元数据, 整份创建或覆盖, 删除}；
拒绝集 = {按只读打开, 按追加打开}。**

### 由此可以排除的

- 文件损坏 / 权限位 / 属主 —— `stat` 正常，别的进程同时写得进去。
- 并发写入打架 —— 拒绝的是 `open` 本身，不是锁。
- 数据根走错 —— 走对了，`stat` 和 `ls` 都命中同一批真实文件。
- 「二进制被替换导致 TCC 作废」—— 本次窗口内没有任何安装动作。

### 仍然不知道的（**不猜**）

**谁在发这个 EPERM、以及为什么会在运行中翻面。** 允许集/拒绝集这个形状很像一条
沙箱/TCC 规则，但**本文件不给成因**——上一版就是因为把推测写进标题而被降级过一次。

**下一个接手的人，第一件该做的是**：在故障当口跑一次带 `-f` 的系统调用跟踪
（或用 `sandbox` 日志 / `log stream --predicate 'subsystem == "com.apple.TCC"'`），
把发拒绝的那一层抓出来。**允许集/拒绝集已经给了它一个很窄的靶子。**

### 同一窗口的第三个独立观察：**测试套件在故障中会报绿，不会报红**

「给 pbxproj 生成加痕迹」那趟全量恰好落在同一窗口里（我量到 EPERM 是 11:27:12，
它 11:27:23 开跑）。结果不是失败，是 **3 条测试只在那一趟 skip** ——
`CrewMentionFilterRealWhiteboardTests` 那一族，昨天 passed、之后重跑也 passed。

机制它追到了源码：

```swift
guard let data = try? Data(contentsOf: url) else { continue }
```

**`try?` 把读失败吞成「没数据」→ 一路走到 `XCTSkip`，而且那个 skip 连原因都是空的。**
它另外量了那个目录：55 个文件全部可读、1067 行 `senderKind:"user"` —— **不是真的空。**

**所以故障发生的那一趟，整套测试报 `0 failures`。**
skip 不刺眼、没有原因、还被算进绿里。

**这条的适用面比 EPERM 大**：任何「读不到就当没有」的测试，在环境坏掉时都会

（`79a1a72`）同一个主人。那个 `try?` 要不要改成「读失败要么红、要么 skip 但写明原因」
一并归它判。

## 2026-09-09 14:00 第二次现场：**上一节有一句话要更正 —— 它确实跟 inode 有关**

窗口又开了（`post_to_crew` 和 `plan_update` 双双如实报错）。这一趟做了上一趟没做的两个实验，结论**推翻了上一节的一句断言**。

### ⚠️ 更正

上一节写的是：

> 跟文件来历、inode、已有还是新建**全都无关**。

**「跟 inode 无关」这句是错的**，当时只做了「自己新建的文件也读不了」这一个实验就下了结论，
而那个实验分不出「按路径判」和「按 inode 判」——**新建的文件也在同一个目录里。**

### 这一趟补的两个实验，把它分开了

| 实验 | 结果 | 排除了什么 |
|---|---|---|
| 换路径字符串读同一个文件（`/System/Volumes/Data` 前缀） | **EPERM** | 不是按路径字符串匹配 |
| `link()` 硬链接到 `/tmp`，再读那个链接 | **`link()` 成功；读链接仍 EPERM** | **禁令跟着 inode/vnode 走，不跟着路径走** |

**所以正确的说法是**：目录里的文件（含我自己刚创建的）带着这个禁令，
**而且把它硬链接到目录外面，禁令照样跟过去。**

### 允许集/拒绝集（这一趟复量，并新增两项）

**允许**：`getdirentries`、`stat`、`open(O_WRONLY|O_CREAT|O_TRUNC)`、`unlink`、**`link()`**
**拒绝**：`open(O_RDONLY)`、`open(O_WRONLY|O_APPEND)`、**读扩展属性（`xattr -l`）**

### 这一趟排除掉的两条

- **不是 ACL**：`ls -lde` 在目录和文件上都没有任何 ACL 条目（mode 里也没有 `+`）。
  这条假设看起来很像（macOS ACL 的确能分别 deny `read` 和 `append`），**实测否掉了。**
- **不是 `chflags`**：`ls -lO` 显示标志位为空。

### 两条新事实

1. **禁令是按进程分的，不是全机的。** 同一个文件 `quota.json` 的 mtime 是 **13:55:05**，
   而我 **14:00** 读它是 EPERM —— **五分钟前有别的进程写进去了。**
2. **我的进程链是**：`zsh → claude → PendingCrew --daemon → launchd`。
   也就是说**被拒的这个进程，它的祖先就是 PendingCrew 自己。**

### 找过但没找到的（是读数，不是结论）

`log show --last 3m` 里**没有任何提到 PendingCrew 的 sandbox/deny 记录**
（`eventMessage CONTAINS[c] "deny" OR CONTAINS "Sandbox: "` 全表 grep 无命中）。
**所以它不是走 sandboxd 那条会记日志的路** —— 或者那条日志在别的子系统里，我没找到。

### 仍然不写成因

允许集里有 `link()` 和「整份创建覆盖」、拒绝集里有只读打开和读 xattr、禁令跟 inode 走、
不进 sandbox 日志、按进程分 —— 这几条合起来指向一个很窄的范围，但**指向不等于证明**。
下一次撞上，该做的是在窗口内拿到发拒绝的那一层（内核 MAC 策略的名字），而不是从形状反推。

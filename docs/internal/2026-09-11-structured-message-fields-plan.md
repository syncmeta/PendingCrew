## 0. 一句话

人类这三条要的是同一件事：**发言的时候把「给谁看、这是什么、结论是什么」说出来，
别让界面去正文里猜。** 而仓库里**两件已经建好的东西从来没被接上**，
所以今天界面只能靠猜。

## 1. 现状（实证，不是转述）

### 1.1 折叠摘要确实是「第一个加粗」——人类说对了

- `Sources/Models/CrewMessageFold.swift:54-63` — `fold(_:threshold:explicitSummary:)`：
  先用 `explicitSummary`，没有才 `derivedSummary`。
- `:71-76` — `derivedSummary` = **前 3 段里的第一个 `**粗体**`**，再没有才找第一个标题，
  都没有就不折。
- `:94-101` — `firstBold` 就是找第一对 `**…**`。

### 1.2 ⚠️ 但那个「可靠的一级」**一次都没跑过**

> **⚠️ 这一小节 2026-09-12 起已经不成立了，留着是为了看得懂当时为什么这么判。**
> 那条路现在**通了**：参数叫 `headline`（**不叫 `summary`** —— 下面文字里那个
> `summary` 从来没在代码里存在过，别去找它），schema 里有、落盘有，
> `CrewFoldableMessageText` 也真的把它传给了 `fold(explicitSummary:)`。
> 所以下面「schema 里没有」「整条路不存在」那几句，读的时候要当成历史。

- `explicitSummary` 全仓 **0 个调用点**（除定义本身）。
- `CrewMessageFold.fold` 全仓**唯一** call site：
  `Sources/Chat/Adapter/CrewFoldableMessageText.swift:26` → `CrewMessageFold.fold(text)`，
  **不传 `explicitSummary`**。
- `post_to_crew` 的 schema 里**没有 `summary` 参数**；白板落盘也**没有 summary 字段**。

也就是说：那段注释写着「发送者显式给的摘要（`post_to_crew` 的 `summary`）」，
而那条路**整条不存在**。**每一条折叠消息的标题，从上线到今天，都是猜出来的。**
人类抱怨的正是这个。

### 1.3 分类（#112）**至今仍是可选的**

- `Sources/Mcp/McpServer.swift:223` — `post_to_crew` 的 `"required": ["message"]`。
  只有 `message`。
- `Sources/Models/CrewMessageCategory.swift:106` — `guard !raw.isEmpty else { return .noLedger }`：
  不给分类 = 不落账，照发。

#115 当时写明「收口（缺参数就拒）留到装版之后 —— 那时所有 session 都在新 helper 上」。
**那一步没有人做。** 所以 #112 的账其实只落了一半：想落账的人落得了，不想的人照旧。

### 1.4 收件人：`@人` 的筛选已经取并集了，漏的是**另一类**

`Sources/Chat/Adapter/CrewMentionFilter.swift:1-50` 里有一份 2026-08-23 的统计
（52 个白板 5257 条）：结构化 578 / 正文 357 / 并集 712。

**那份读数三周没重量过，所以我重量了一次**（2026-09-11，同机、**用生产那把尺子本身**
`CrewMentionFilter.bodyMentionsHuman` 跑真实语料，不另写一套匹配）：

| | 2026-08-23 | 2026-09-11 | |
|---|---|---|---|
| 白板文件 | 52 | **48** | |
| 消息 | 5257 | **12765** | 2.4× |
| 结构化 human mention | 578 | **2718** | 4.7× |
| 正文写了 `@人` | 357 | **761** | 2.1× |
| 两者都有 | 223 | **499** | |
| 并集 | 712 | **2980** | |

**结论变了一半**：agent 现在绝大多数会传结构化 mention 了，但**并集仍然必需** ——
只认结构化仍会漏 **262 条**（761−499）他确实被点名的消息。取并集那条不用改。

筛选器**已经取并集**，所以「正文写了 @人 但没传 mentions」不会漏。

**真正漏的是第三类：压根没 @ 过、但确实是写给人看的那些**——
比如一份四栏汇报。人类的「仅 @ 人」筛选默认是开着的（#128），于是它看不见。
这就是 #142 那句「避免给人的消息不能通过仅 @ 人筛选」。

同一趟量到的第三类规模：

- agent 发的消息 **11613** 条，其中两边都没点名人类的 **8635 条（74%）**；
- 只看**机长**发的（机长是往人类那儿汇报的那一档）：**4598** 条里 **3297 条（71%）**
  两边都没点名。

⚠️ **这两个数是上界，不是问题的大小。** 它们证明的是
「有多少条在『仅 @ 人』筛选下他看不见」，**不是**「有多少条本该给他看」——
那 8635 条里绝大部分是 agent 之间的往来，本来就不该进他的视野。
**这一栏无法从数据里分出来**：今天没有任何字段记着「这条是写给谁的」。
**而那正是 #142 要加的东西** —— 所以这个数的真正用途是：
**在加上收件人字段之前，这个问题的大小是测不出来的。**

顺带一条与 #142 直接相关的：`question` 的账本映射是 `.none`
（`CrewMessageCategory.swift:59`）——**问题不落任何账**。
它又最需要有人回答。没有收件人 + 不落账 = 一条问出去就没了的消息。

## 2. 方案：三件事合成「发言前必须声明的三样」

不新起一套，**全部加在 #112 已有的那套上**（`CrewMessageCategory` /
`CrewCategoryRouting` 已经有完整的「必填 + 缺了给出路 + 旧值降级」的形状，照抄它）。

| 声明 | 参数 | 回答什么 | 现状 |
|---|---|---|---|
| 给谁看 | `mentions`（已有） | 这条是发给谁的 | 有，但可省；省了 = 广播 |
| 这是什么 | `category`（已有） | 落哪本账 | 有，但可省；省了 = 不落账 |
| 结论是什么 | `summary`（**新**） | 收起态那一行 | **纯层有形参，外面整条路不存在** |

### 2.1 广播怎么共存（4-1 的问题 ②）

**不用新概念**：`mentions` 里早就有 `{kind:"broadcast"}` 这个**显式放宽器**
（`McpServer` schema 里写着，`CrewWhiteboardVisibility` 认它）。

所以「必须指定接收者」= **把「不填 = 广播」从默认改成必选**，
而「全组」仍然是一个完全合法的答案，只是要显式写出来。
广播一条都发不出去的情况不会发生，改变的只是**得说一声**。

代价是每次发言多一个判断；收益也正是这个 —— 说不出这条给谁看的消息，多半本来就不该发。

### 2.2 `summary` 怎么定义

- `post_to_crew(summary:)`，落盘一个新字段，`CrewFoldableMessageText` 传给
  `fold(explicitSummary:)` —— **那条路已经写好了，只是没人接**。
- 给了就用它；**没给才退回今天的猜**（粗体/标题）。所以接线本身不改变任何现有消息的显示。
- 短消息（不到折叠阈值）也收 `summary`，但不显示——它仍然进白板，
  以后「列表里只看结论」这类需求不用再改一次数据。

## 3. ⚠️ 要人类拍的一条：「必填」是拒收，还是降级 + 标记

**这条我们不替他定。**

- 2026-09-08 他说过：「不是强制一定要干嘛的问题，是**意识和整理**的问题」——
  当时否掉了一个硬闸。
- #143 他自己写的是「结构化信息**必填**的一部分」。

**两句话指向不同的落地方式，需要他确认口径：**

- **A 硬闸**：不给 `summary` / 不给收件人 → **拒绝发送**，错误信息里给出路。
  账最干净，代价是**改错了全组一起哑**（所有 agent 的每一次 `post_to_crew` 都走这条路）。
- **B 降级 + 标记**：缺了照发，但气泡上留一个可见的「这条没写结论 / 没指定收件人」标记，
  且回执里说一句。不哑，但靠自觉的那一半还在。
- **C 分类分档**（我倾向）：`human_todo` / `question` / `blocked` 这些**必须有人接**的
  强制；`ack` / `note` 这类不强制。理由：人类的痛点是
  「**给人的消息看不见**」和「**摘要是猜的**」，这两件都集中在「要人接」的那几类上，
  而 `ack`（「收到」）强制写结论只是徒增仪式。

### 3.1 不管选哪个，落地都必须两步

**这是硬约束，不是偏好**：`--mcp-serve` 是**一 session 一进程、长期存活**的
（见 `LocalSessionLaunch` 里那段「两条腿」的注释）。改了 MCP 契约，
**在跑的 session 不会生效，直到它被换掉**。

所以：

1. **第一步（现在能做）**：加参数、加降级提醒、加渲染。缺参数**一律不失败**，
   只在回执里说一句。
2. **第二步（装版之后）**：所有 session 都在新 helper 上了，才把闸收紧到人类要的那一档。

#115 就是这么落的，而且**第二步至今没做**（见 1.3）——
所以这次要把「第二步由谁、在什么时候做」明确成一条待办，否则它又会挂在那儿。

## 4. 老消息怎么办

**不迁移、不回填、不标记。** 老消息没有这些字段，就按今天的样子显示
（折叠摘要仍走猜，收件人仍是广播）。理由与 #115 当时一致：
迁移历史数据的收益远小于风险。代价是「有标记/没标记」在一段时间内混着出现，
这是可接受的 —— 它本来就如实反映了「这条是老的」。

## 5. 边界

- **本文没有验证任何界面表现。** 1.1–1.4 全部是**读代码读到的**（带 file:line），
  不是在跑着的 app 上实测的。
- 2.1 说的「广播仍然发得出去」是基于 `broadcast` 这个 kind 今天已被
  `CrewWhiteboardVisibility` 认；**没有实测**一条只带 `{kind:"broadcast"}` 的消息
  在筛选器下的表现。
- 1.4 的读数**已经重量过**（2026-09-11）。量法记在这里以便复核：
  一个临时测试遍历 `~/Library/Application Support/PendingCrew/whiteboards/local-*.json`
  （排除 `*todos*`），逐条调 **生产代码本身** `CrewMentionFilter.bodyMentionsHuman`，
  花名册取 `humanNames: ["人"]`（本机人类显示名的兜底）+ `otherNames` = 该 crew 白板里
  出现过的全部 `senderName`。测完删了，没进仓库。
  **两处口径差异要说清**：① `otherNames` 是从发送者名**近似**出来的，
  不是真花名册 —— 名字越多，越可能有更长的成员名盖住「人」，所以
  **正文命中数 761 是下界**；② 语料是活的，同一趟测量期间它从 12761 长到 12765
  （我自己在群里发言），所以这些数是「那一刻」的。
- **旧读数那份注释本身值得单独记一笔**：它不是写错了，是**三周前写对、现在只对一半**。
  引用它的人没办法从注释里看出这一点 —— 这正是「静态文本描述会变的事实」。
- 「改错了全组一起哑」是推论，不是观测：没人实验过一个坏的必填闸对在跑 session 的影响面。

# Apple Development qualification, not ordinary product activation

The human confirmed Team M42BKJN82S, bundle/topic com.pendingname.pendingcrew, CloudKit container iCloud.com.pendingname.pendingcrew, PCWPersonalBranch with collectionID:String QUERYABLE and payload:Bytes, and APNs Sandbox. These are public inputs, not proof of a signed App or successful Apple exchange. Existing installed ordinary/HotReload builds remain unqualified.

Use the original Debug target and its App-owned ignored Config/Local.xcconfig. Set PENDINGCREW_APPLE_SERVICE_CONDITIONS to PENDINGCREW_APPLE_CLOUD_DEVELOPMENT, PENDINGCREW_APPLE_APNS_SANDBOX, or both, only after matching profiles are qualified. Do not pass these or App signing selectors globally to SPM. No new target/configuration/scheme is needed. Launch the private test App with one shared lowercase canonical UUID in PENDINGCREW_APPLE_QUALIFICATION_RUN_ID; missing/invalid UUID or a different bundle is unqualified. The runtime variable is only a test partition identifier and never authenticates a signature, Apple account or Core.

Cloud-only uses Resources/AppleCloudDevelopment.entitlements. Combined Cloud+APNs uses Resources/AppleDevelopment-macOS.entitlements or Resources/AppleDevelopment-iOS.entitlements. All preserve the original two Keychain groups. The Cloud-only template intentionally has no APS; combined templates have only the platform-correct APS development claim. No KVS entitlement is added. Existing normal distribution sign-only code accepts its old closed claims and cannot silently sign these templates; a separate exact reviewed Development signing invocation is required, using actual applicable profiles. Never copy the whole profile entitlement dictionary into the App.

Before any App build/launch, require the actual M42 explicit AppID/profile to allow the exact container/CloudKit/Development and, if APNs is selected, the platform APS development claim. The App uses CloudKit private database/default zone. Signed iCloud-container-environment chooses the actual server environment; the Swift .development field merely labels its account partition. Final signed entitlements, embedded profile, identity and source must be independently checked. Current local a081/fbb profiles lack all Cloud/APS claims; they cannot qualify this activation. No allowProvisioningUpdates, new certificate/device or Apple resource operation is authorized by this document.

Cloud and APNs compile independently. Cloud collections are qualification.<runUUID>.drafts and qualification.<runUUID>.hosts, distinct from normal drafts/hosts and from each other; do not put production data into them. Use a new private frontend data root on each test device, retain the same run UUID on reopen, and require the existing explicit per-user cloud opt-in. Initial unqualified/Release/HotReload paths return nil. HotReload configureRuntime still injects configuration:nil. KVS stays nil/off; current optional appearance sync is not enabled here. No account discovery or upload is performed by qualification construction.

APNs qualification only supplies Sandbox and topic. Actual permission/token registration still requires the original explicit user opt-in, current authenticated mTLS recipient grant/selection/origin, matching enabled Core provider and no unresolved original registration. Local Human is not a recipient. Provider p8/keyID/configuration stay server-side; this source contains no key/path/token and does not create a provider or pair a device. No background/model/session action is introduced.

The retained apple-service-qualification Swift fixture runs the actual pure qualification source slice in ordinary, Cloud-only, APNs-only, combined, HotReload and non-Debug compile modes. This proves configuration selection/missing-invalid scope/collection partitioning only, not full App compilation, profile eligibility, CloudKit exchange, APNs registration or delivery. System iCloud login, permission and actual device access require normal user handling; no TCC/Keychain/account bypass is part of this unit.

# Apple Development Cloud configuration and optional qualification

The human confirmed Team M42BKJN82S, bundle/topic com.pendingname.pendingcrew, CloudKit container iCloud.com.pendingname.pendingcrew, PCWPersonalBranch with collectionID:String QUERYABLE and payload:Bytes, and APNs Sandbox. These are public inputs, not proof of a signed App or successful Apple exchange. Ordinary builds without the explicit flags, Release and HotReload remain unqualified.

Use the original Debug target and its App-owned ignored Config/Local.xcconfig. Set PENDINGCREW_APPLE_SERVICE_CONDITIONS to PENDINGCREW_APPLE_CLOUD_DEVELOPMENT, PENDINGCREW_APPLE_APNS_SANDBOX, or both, only after matching profiles are qualified. Do not pass these or App signing selectors globally to SPM. No new target/configuration/scheme is needed. `Config/AppleDevelopment.xcconfig.example` is the explicit opt-in combined local-device overlay; it is not included by default. Copy it into the App-owned ignored Local.xcconfig only in a coordinated build scope after the exact profiles/certificate/device are verified. It selects the platform-correct Development entitlement template and keeps Simulator conditions empty. Never replace an existing personal Local.xcconfig without preserving it. The explicit Cloud Development build and exact normal bundle provide Cloud configuration during normal opening, without launch environment variables. The existing per-user confirmation is still required before account access or synchronization.

Only explicit test runs supply one shared lowercase canonical UUID in PENDINGCREW_APPLE_QUALIFICATION_RUN_ID. If this key exists but is empty or invalid, Cloud remains unqualified; it must never fall back to normal collections. A different bundle is always unqualified. This runtime variable is only a test partition identifier and never authenticates a signature, Apple account or Core. APNs is also configured for normal no-environment opening when its explicit App-only Sandbox flag is present in a qualified Debug build. If a qualification key is explicitly supplied, it must be a valid lowercase canonical UUID; an invalid value remains unqualified. Configuration selection does not request OS notification permission or register a device.

Cloud-only uses Resources/AppleCloudDevelopment.entitlements. Combined Cloud+APNs uses Resources/AppleDevelopment-macOS.entitlements or Resources/AppleDevelopment-iOS.entitlements. All preserve the original two Keychain groups. The Cloud-only template intentionally has no APS; combined templates have only the platform-correct APS development claim. No KVS entitlement is added. Existing normal distribution sign-only code accepts its old closed claims and cannot silently sign these templates; a separate exact reviewed Development signing invocation is required, using actual applicable profiles. Never copy the whole profile entitlement dictionary into the App.

Before any App build/launch, require the actual M42 explicit AppID/profile to allow the exact container/CloudKit/Development and, if APNs is selected, the platform APS development claim. The App uses CloudKit private database/default zone. Signed iCloud-container-environment chooses the actual server environment; the Swift .development field merely labels its account partition. Final signed entitlements, embedded profile, identity and source must be independently checked. Old a081/fbb profiles lack Cloud/APS claims. The separately qualified Mac 0fedf688-4ca5-47e8-9d43-e09afd4776f7 and iOS 774bbb92-be03-48b7-b65c-f1dccc54b339 profiles allow them; their exact hashes, BF947 identity and device membership remain build gates. No allowProvisioningUpdates, new certificate/device or Apple resource operation is authorized by this document.

Cloud and APNs compile independently. Normal Cloud opening uses drafts and hosts; an explicit qualification run uses qualification.<runUUID>.drafts and qualification.<runUUID>.hosts. These collections are distinct, and no data is migrated or copied between them. The old Mac qualification sample is not evidence that a normal iPhone sees those same records. Normal two-device synchronization needs matching normal configuration and account on both devices. Normal opening retains the existing frontend root; explicit tests retain their separately selected private roots and shared run UUID on reopen. The original per-user opt-in and account namespace fences remain in force. Unqualified/Release/HotReload paths return nil. HotReload configureRuntime still injects configuration:nil. KVS stays nil/off; current optional appearance sync is not enabled here. Configuration construction performs no account discovery or upload.

APNs configuration only supplies Sandbox and topic. Actual permission/token registration still requires the original explicit user opt-in, current authenticated mTLS recipient grant/selection/origin, matching enabled Core provider and no unresolved original registration. Local Human is not a recipient. Provider p8/keyID/configuration stay server-side; this source contains no key/path/token and does not create a provider or pair a device. No background/model/session action is introduced.

The retained apple-service-qualification Swift fixture runs the actual pure qualification source slice in ordinary, Cloud-only, APNs-only, combined, HotReload and non-Debug compile modes. This proves configuration selection/missing-invalid scope/collection partitioning only, not full App compilation, profile eligibility, CloudKit exchange, APNs registration or delivery. System iCloud login, permission and actual device access require normal user handling; no TCC/Keychain/account bypass is part of this unit.

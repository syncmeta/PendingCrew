## 01:02 补三条读数（都是量的）

**① 载体：目录**赋予、**inode** 携带 —— 旧记录和我上面那句各对一半。

`link()` 建硬链到一个完全正常的目录（允许集里有 link，确实成功了），

## 01:18 —— 一个天然对照实验把成因收窄到一句话

### 读数

| 谁 | 二进制 | 它的父链 | 能不能开那些文件 |
|---|---|---|---|
| daemon（pid 53445） | `PendingCrew` | GUI app 直接起的 | **能**（此刻仍在写 `crew-sessions.json`，0 分钟前） |
| MCP helper（pid 53687） | **同一个 `PendingCrew` 二进制** | `claude` 起的 | **不能**（`post_to_crew` 失败回执点名的就是它） |
| 我的 shell | `/bin/zsh` | `claude` 起的 | 不能 |

**同一个二进制、不同的父链、相反的结果。** 变量只剩一个：中间那层 `claude`。

### 补测：所有 open 模式

```
O_RDONLY  ❌   O_RDWR  ❌   O_WRONLY  ❌   O_RDONLY|O_NONBLOCK ❌
```

**打开既有文件一律被拒，不分模式**；而**新建文件仍然可以**（`O_CREAT` 那条路）。
这比 09-08 那份记录更准：当时写的「`open(O_WRONLY|O_CREAT|O_TRUNC)` 允许」
说的其实是**创建新文件**，不是「以写方式打开既有文件」。

### 成因（现在有机制、有对照、能解释间歇性）

**macOS 把 TCC 的「责任进程」算在最近的那个已签名 app 上。`claude` 是一个独立签名的
可执行文件，它在链上把责任从 PendingCrew 截断了** —— 于是它底下的一切
（包括 PendingCrew 自己的 helper 二进制）都以「claude 的身份」去访问
PendingCrew 的 app 数据，而 claude 没有这个权限。daemon 不经过 claude，所以没事。

**这也解释了为什么它是间歇的**：责任归属是**按进程缓存**的。
今晚 00:11 换了 app、00:24 重起了 daemon，**之后新生的 claude 进程拿到的是新的
（被拒的）归属**；而在那之前起的进程沿用旧归属，所以我整晚都读得好好的，
直到这一批进程换代。09-08 那四次现场同样都紧跟在装版之后。

**仍然是假设，缺的证据**：没抓到系统日志里那条拒绝（`log show` 无命中，
大概要 `sudo log stream`）。上面那张表是对照，不是日志。

### 所以人该给谁授权

**不是给 PendingCrew，是给 `claude`（或它所在的终端）。**
系统设置 → 隐私与安全性 → **App 管理** / 完全磁盘访问。

（它们全部经由 claude → helper 这条链）。

- **Endpoint Security 客户端**：本机只有一个系统扩展，是 sing-box 的**网络**扩展，
  不碰文件。没有任何 EDR（falcon/sentinel/santa/defender/… 逐个 grep 过）。
- **MDM / 配置描述文件**：无企业注册。

所以：不是权限位、不是 flags、不是 ACL、不是 TCC（无日志）、不是沙盒（无日志、
且关掉 agent 自己的沙盒也一样）、不是 ES、不是 MDM、不是签名、不是 provenance、
不是磁盘满、不是进程谱系。

**十条排除完，我举不出第十一个候选。** 这份记录到此为止 ——

## 08:05 定性完成：**不是「这些文件」的事，是「已经存在的路径」的事**

一直没人做的那个实验只花了两分钟：**自己在那棵树里新建一个文件，再打开读它自己。**

```
① open(新路径, O_CREAT|O_WRONLY)      ✅
② open(同一个路径, O_APPEND)          ❌ EPERM
③ open(同一个路径, O_TRUNC)           ❌ EPERM
④ stat(同一个路径)                    ✅ 4 字节
⑤ open(同一个路径, O_RDONLY)          ❌ EPERM
⑥ mkdir(树里的新子目录)                ✅
⑦ 在那个新子目录里新建文件              ✅
⑧ 读⑦刚建的那个                       ❌ EPERM ← **整棵子树，不是某几个文件**
```

### 规则一句话

**可以 `stat` / 列目录 / `mkdir` / `unlink` / `open(O_CREAT)` 一个不存在的路径；
永远不能 `open` 一个已经存在的路径 —— 读、写、追加、截断，一律 EPERM。**

### 横向对照（同一条探针，同一个进程，同一分钟）

| 目录 | 新建后读回来 |
| --- | --- |
| `Application Support/Codex` | ✅ |
| `Application Support/Claude` | ✅ |
| `Application Support/Google/Chrome` | ✅ |
| `Application Support/PendingCrew` | ❌ |

### 它推翻了什么

- **「写照常」是错的**（那张老表里写着 ✅）。写只有**新建**那一种成立；
  往已存在的文件里写同样被拒。白板 append 是读-改-写，所以它必然失败 ——
  `post_to_crew` 拒绝得对。
- **凡是「这些文件被做了什么」的假说全部出局**：xattr / provenance / flags / ACL /
  归档状态 / 内容损坏 —— 我**自己刚建的**文件，建完那一刻起就打不开了。
  九条死路里有四条（硬链、四份历史备份、所有 open 模式、直接读）本质都在这一族里。
- **也不是「整个 Application Support 被锁」**：另外三个 app 的同类目录同一分钟正常。
  拦的是**这棵子树**。

**「谁被拦」还是没定**：这条探针只证明**这个进程**被拦。daemon 手上那些 fd

### 结论：**故障期间 daemon 也 open 不了既有文件**

排空必须先 `open` 那个文件。窗口里它一次都没成功，窗口外不到一秒就成功 ——
**消费那一侧（app / daemon）在窗口里跟 agent 这一侧一样瞎。**

这否掉了这条账上挂了很久的一句话：「产品本身不坏，瞎的只有 agent 这一侧」。
**那是 09-08 那次的结论，不是通则。**

### 方法上值得留的一条

**这个读数是「入队本身」给出的** —— 群聊发不出去（append 要先读），但
`message_child_crew` 的入队是新建文件、属于放行那一侧。所以「给子机组带句话」这个
**本来就要做的动作**，同时就是探针。不用为实验白花一次动作。

**而它单独不成立**：窗口内那 43 分钟，在拿到「正常 < 1 秒」之前说不出是症状还是常态。
今天特意等窗口过去补了那一趟，两个数一起才构成判据。

## 17:43 第三次窗口：**禁令跟 inode 走，不跟路径走**（不用 sudo 就拿到了）

窗口第三次开（09:11 恢复 → 10:41 又断 → 11:26 恢复 → **17:43 再断**）。
趁它开着做了一个两分钟的实验，把这条账上两句各自成立、却从没被合起来的话接上了：

```
① 在树里新建一个文件                 ✅
② 走原路径读它                        ❌ EPERM
③ 硬链到 /tmp（同一个 inode、路径在树外） ✅ 建得了
④ 走 /tmp 那条路径读                  ❌ EPERM
   对照：/tmp 里一个普通新文件          ✅ 读得了
```

### 合起来的那一句

> **任何「诞生在那棵树里」的 inode，此后无论从哪条路径去开都被拒；
> 树外诞生的 inode 正常。**

**它一刀切掉两整族假说**：

- **不是按路径判的** —— 硬链到树外，换一条路径去开，照样拒。
- **不是「那些老文件被做过什么」** —— 我**自己刚新建**的文件一样中招（今天上午已证）。

这两句以前分别记过（8-2x 记过「跟着 inode 走」，今天上午记过「自己新建的也打不开」），
**但没人把它们放在一起** —— 放在一起才逼出「按出生地判」这个形状，
而那正是系统级数据保护（容器归属）的形状，不是文件系统权限的形状。

### 边界

它说的是**按什么判**，不是**谁在判**。「哪一层发出这个拒绝」仍然只有
`sudo log stream --predicate 'subsystem == "com.apple.TCC"'` 或 `sudo fs_usage` 能回答，
挂在人类 Todo #19。**别拿这一条去替代那一条** —— 形状对得上不等于就是它。
